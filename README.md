# Dr. Saeed Ghezelbash — dist-first static source

Static Astro source for <https://www.ghezelbaash.ir/>.

## Build

```bash
npm ci
npm run build
```

Use Node 24.19+ within major 24 and npm 11.9+ within major 11. `scripts/build.mjs` is the single build entry: it produces the complete static website in `dist/`, serializes the graph to RDF, exports the authored readable and machine formats, and checks the finished files. It also verifies that neither canonical file nor the editorial guide and implementation policies changed during the build.

This is a finite static distribution: a comprehensive home, focused direct-entry HTML for every authored content path, a 404 fallback, assets and machine formats. Cloudflare's connected Git integration publishes main. No runtime server or bot-specific response is required. Direct entry automatically loads the complete guide in place and positions the reader at the requested topic, so preceding and following content is available by scrolling. Navigation and expansion stay within one document.

## The two canonical files

- `src/content-source/page.md` owns only the human-authored HTML body: headings, links, media markup, embedded Microdata and the single browser-JSON-LD placeholder. It has no YAML frontmatter or configuration registry.
- `src/data/semantic/knowledge-graph.jsonld` owns entity facts, identifiers, relationships, semantic distribution identities, Dataset versions, DOI history, image rights and explicitly authored evidence assessments.

`src/lib/canonical-inputs.mjs` reads these two canonical sources and derives lifecycle, evidence and browser JSON-LD. The current Dataset is selected through one explicit `datasetId` bootstrap in `src/config/site-policy.mjs`; historical Dataset nodes are never selected by guessing. Canonical input loading does not parse YAML or compose a page-metadata object.

`src/config/site-policy.mjs` exports individual rendering, UI, navigation, discovery and retrieval policy domains. Components and projections import only their actual inputs. Display title and primary language are presentation choices; direction is derived from that language. The homepage description, social image, physician identity, release and review facts come from the graph. Explicit social regions and the compact hero preload remain rendering choices. Reviewed equivalent-question groups live in `discoveryPolicy`; each member must resolve to its actual self-canonical Question route and language.

`src/config/machine-resources.mjs` owns the finite delivery/materialization registry. It declares output paths, source artifacts, targets, head/footer labels, descriptor roles and delivery exceptions. `resources.mjs` resolves distribution media types, semantic titles and profiles from the graph rather than repeating them in policy. Resources without graph-owned distributions retain explicit delivery media types.

`src/content-source/llms-guide.md` is separately authored editorial retrieval guidance, read directly by projections and published unchanged as `llms.txt`. It is neither visible page content nor another factual graph. It is not templated from entity facts.

Consumers select and format existing data; they do not persist parallel entity, release or evidence truth. Evidence observations are copied faithfully, including absent status or date values. A build does not claim a new external verification.

The current Dataset release label is `1.3.3`. Historical DOI records retain their actual versions and publication dates. Updating the current content does not automatically increment that label. Publication dates and the current Dataset revision date describe different events.

The page contains concrete authored values. There are no contact, release, image-size, or image-Microdata placeholders to inject at build time; the sole semantic build-time placeholder is the browser JSON-LD script, whose document is projected from `knowledge-graph.jsonld`. When an authored fact changes, update the corresponding graph data and visible page text where applicable. Editorial retrieval prose is maintained separately in `llms-guide.md`.

Microdata is HTML markup. ImageObject attribution and licensing are stored directly on the canonical page's image figure. The image binaries are static assets; HTML Microdata is not inserted into them.

## Presentation and generated files

The complete canonical content file is already HTML. `index.astro` renders it directly through `canonical-page-html.mjs`; there is no generated Markdown copy or second front matter parse. The page authors one empty browser-discovery script placeholder. `page-discovery-jsonld.mjs` deterministically selects and localizes the browser graph from `knowledge-graph.jsonld`, including numeric image dimensions and the visible FAQ relationship; the renderer injects that projection and escapes `<` for safe HTML embedding. The placeholder follows the visible introduction so streamed HTML can paint the portrait and heading before receiving the complete browser graph; its entities and values are unchanged. The full multilingual graph remains the authority for facts and focused route projections, which omit optional ProfilePage timestamps when only a calendar date is known. The complete, byte-identical `graph.jsonld` and RDF exports retain historical events, self-hosted reviews and external profile evidence. Medical text and whitespace are preserved. The native guide launcher is authored as a link, and the image creator is authored as a typed Person in Microdata; the page uses JSON-LD without a competing URL-valued ProfilePage Microdata scope.

`src/styles/global.css` contains the static presentation and finite chunk-height estimates. Content visibility defers offscreen layout and remembers measured heights; estimates vary with device fonts and viewport. The reader fills a bounded page width, with a single-column introduction through tablet widths and full-width prose beneath the desktop portrait. Mobile tables preserve readable column widths, expose a scroll hint and remain keyboard-focusable. Astro components provide layout. The small progressively enhanced search/navigation runtime lives in `src/scripts/guide-runtime.js` and is minified at build time into one inline script with an exact CSP hash. `public/` contains media and browser assets. Static route aliases, media aliases, HTTP-header templates and SHACL shapes are technical delivery or validation inputs.

After changing layout dimensions, run `npm run build`, then `BROWSER_EXECUTABLE=/path/to/chromium npm run calibrate:layout`, then rebuild. Calibration uses the built page and its loaded fonts at six viewport widths to refresh render-chunk estimates without changing content; it requires a locally installed Chromium browser. The chunk inventory is measured, not fixed. A diagnostic report is written to `.generated/layout-calibration.json`.

Generated files live in `.generated/` and `dist/`. File hashes, RDF measurements, build identity and Content Security Policy hashes are measured from outputs and do not become canonical authoring requirements. No fixed graph, answer, passage or resource totals are required.

`npm run validate:dist` checks canonical head values, search destinations, image rights, exact graph publication, actual internal links and media resources, metadata routes, faithful evidence projections and the absence of legacy placeholders. The normal build also crawls emitted native links from home to every topic, checks breadcrumb ancestry and records duplicate initial scopes. It checks HTML structure, the browser discovery projection, descriptor integrity and Cloudflare's static rule limits. Passage extraction preserves H1 through H6, including headings nested in disclosure summaries, and records their authored heading ancestry. Each answer atom must retain its actual Answer source URL. Passage provenance records only explicitly known source revisions and includes the actual answer sources; it does not substitute an archived release date for an unknown revision.

## Content paths

Every finite authored content path has its own physical HTML file, self canonical, title, description and page node with a typed mainEntity. Named entities and questions reuse their graph identifiers; other headings derive WebPageElement identities from the actual visible content. A Question that embeds a VideoObject retains Question/Answer as its main subject and keeps video as supporting media. Focused heading ranks start at H2 beneath the route H1 without changing their IDs or medical text. The first heading of a complete section presents its readable introduction when one exists, while the section entry retains all subtopics; these are useful distinct initial views with unchanged self canonicals. Video entry points use their VideoObject, and question pages use FAQPage with the authored accepted Answer. Readable answer paragraphs keep their own scope instead of inheriting an entire parent section. Empty aliases inherit their actual adjacent content region. Breadcrumbs describe the real home and current path. Each path relates to the comprehensive home and WebSite; the shared physician keeps the authored homepage URL, mainEntityOfPage, verified identity links and known qualifications. Each route names the same doctor as author and publisher; typed credential, identifier, membership, medical-practice and education nodes preserve the authored semantic relationships. Document and social titles include the doctor's authored name while visible topic headings remain focused. Social locales use declared regional values. Descriptions use the authored media description, Answer summary or real medical prose instead of browser fallback, chapter controls or navigation. A declared historical disclosure view selects its actual source city summary and describes historical evidence without claiming patient counts or current services in every city. Subheadings without their own topic relation inherit the nearest authored containing section's `about` references. Scoped graphs retain linked medical procedures, biomedical subjects, category terms and their named term registries without importing the registry's complete contents. Each page's `about` includes the fixed physician and these existing topic references. Broad homepage content relationships are not pulled into focused views. The sitemap lists home and all direct entries once, with visible media scoped to each entry. Native parent and immediate-child links follow the authored heading/container hierarchy. The home guide exposes the root branches through a compact disclosure; every finite topic is reachable through actual HTML hyperlinks before JavaScript runs. Breadcrumbs reflect the same ancestry and collapse explicitly equivalent section/heading levels. Repeated labels across different authored contexts include their real parent in document metadata. Only explicit equivalent-question groups emit reciprocal, self-inclusive hreflang links in their HTML and sitemap records; the runtime replaces these links during route navigation. Sorani retains `ckb-IQ` in HTML and RDF while hreflang uses the supported ISO 639-1 Kurdish code `ku-IQ` and Open Graph uses `ku_IQ`. The homepage and untranslated topics do not claim language equivalents.

Question pages retain `FAQPage` alongside their content-specific document type, with their original Question and one accepted Answer. [Google retired FAQ rich results on May 7, 2026](https://developers.google.com/search/updates#deprecating-the-faq-rich-result-feature); this typing does not claim that feature. Open Graph language alternates describe only reviewed equivalent pages, with the same regions as their hreflang declarations. The multilingual home has no translated equivalents and emits no social locale alternates. Its declared locale configuration remains available to resolve generic English topics without inventing a country.

Document types follow the nearest reviewed purpose in the authored topic hierarchy. Diagnosis, treatment, candidacy and safety information use `MedicalWebPage`; biography, research history, reputation, licensing and travel administration use `WebPage`. The dedicated contact scope uses `ContactPage`. Clinical questions retain `MedicalWebPage` plus `FAQPage`, while physician-identity questions use `WebPage` plus `FAQPage`. Only the dedicated physician profile uses `ProfilePage`. The comprehensive home keeps its authored `MedicalWebPage`. An embedded video does not replace a text heading's authored subject: only an actual media target selects `VideoObject` as primary, with visible embedded players linked as supporting parts of text pages. These classifications do not add Article, Event, Review or gallery claims to ordinary headings.

Each build writes `.generated/schema-inventory.json` and `.generated/schema-inventory.csv` for the homepage and every finite content URL. They record actual page types, primary entities, source-purpose evidence, scoped graph identities and content-scope hashes. Distribution validation compares the inventory to the emitted documents; CI retains both files with the validated distribution. The inventory is an internal review artifact, not an additional public page or a second factual source.

Browser graphs retain the existing clinic contact point, service-area country and physician actions as bounded relationship definitions. They do not traverse complete service catalogs. The physician ProfilePage keeps its canonical portrait relationship. Credentials and identity links remain authored facts; a graph projection cannot manufacture independent verification or entity recognition.

The homepage resolves its authored `speakable` specification and the existing Course's historical `CourseInstance`/`EducationEvent`, including their original date, location and audience. This bounded closure does not import unrelated events or create a dedicated event, course-list or voice-search eligibility claim.

Machine-readable passage exports preserve nested authored language groups and direct prose outside paragraph wrappers. Citation sources use existing clean content routes or a real homepage fragment when an element has no independent page. They do not invent clean URLs for every HTML ID. The complete source prose and canonical graph remain unchanged.

The interface stays one page. Direct entry serves meaningful topic HTML, then automatically fetches and inserts the complete home guide before initializing navigation and resolving pathname, fragment or video destinations. The complete guide is fetched once, without changing the current route's canonical or entity metadata. The expansion link remains a native fallback and retry control; no click is needed on a successful load. Existing video elements are reused to preserve playback. Focused HTML exposes authored local posters natively and removes portrait preloads when that image is absent from its initial article; the comprehensive homepage retains its existing media hints. The runtime refreshes search, media posters and navigation after expansion. The body keeps the shared interface's authored Persian language and direction. The complete article explicitly keeps its Persian language and right-to-left direction when route metadata changes to a foreign-language entry; focused articles, route context and multilingual sections keep their own language attributes. Clicking another topic uses History API and scrolls in the existing document while synchronizing language, direction, canonical, title, social metadata and JSON-LD. Native home fragment links work in the same reader. Back/Forward skips fresh deep-link positioning, as does a reader who starts interacting while the initial guide request is pending. Crawlers and readers receive identical HTML and scripts; there is no user-agent branching. Without JavaScript, native links remain usable; failed guide expansion retains the focused topic and offers retry. Guide and route-metadata requests have a 15-second deadline, including reading the response body; navigation and search initialize even if guide expansion times out.

Content paths rely on Cloudflare Pages native clean-URL serving of their physical HTML files; they are not rewritten through .html destinations, which can cause a normalization loop. Exact finite 200 rewrites remain only for legacy and metadata aliases. Legacy aliases preserve their requested URL and retain the target document's canonical. Machine graph/provenance subjects remain machine aliases rather than HTML pages. Static build file format keeps the authored slashless paths. Hosting-level normalization must still be verified independently.

The build moves the 404 document's existing ordered inline CSS into one fingerprinted same-origin stylesheet. This preserves its CSS and body while allowing actual 404 responses to render under an upstream CSP with outdated inline-style hashes. Extraction rejects conditional styles, imports and relative resources that could change meaning. Deployment validation checks the asset fingerprint and inventory; `.generated/not-found-css.json` records the original style digests. The response remains 404 and `noindex`, without weakening CSP.

Self canonical and distinct initial topic documents support separate discovery; Google decides indexing and ranking. Full-guide expansion is automatic for direct entry and uses the same code for crawlers and readers. Schema relationships preserve the homepage identity; they do not guarantee rankings or prevent every canonical consolidation. A comprehensive shared reader cannot guarantee that every small heading becomes a separate search result. Retaining semantic Event, Review, Dataset or Course types also does not guarantee a rich feature. The patient rating (5/5) and workshop day (2025-02-04, 16 Bahman 1403) are user-confirmed authored facts and are shown visibly. Reviews about a clinic on its own site remain subject to Google's self-serving-review policy.

No artificial pageviews or requests are emitted for other paths. Fetching the home as a reader resource is not a separate analytics pageview or a Google search click. Real route navigation and section visibility can be measured by an explicitly configured analytics provider; this distribution does not fabricate activity or add third-party tracking.

## Reviewable build output

CI runs the regression and source-ownership tests and the full build. Pull requests from `codex/normalize-canonical-*` branches also build the base revision under the same CI identity and compare every dist file byte for byte with `scripts/compare-dist.mjs`. `scripts/compare-canonical-content.mjs` separately compares the actual authored page-body bytes, complete graph and editorial guide against that baseline; only this migration comparison understands the legacy content header. Both equivalence reports are retained. Source-only normalization must preserve content whitespace as well as rendered output. Architecture tests prevent legacy metadata objects, direct YAML parsing dependencies and semantic wrapper modules from returning. CI then retains the validated `dist/` and `.generated/dist-manifest.json` with SHA-256 hashes for every final file. Build identity records the checked-out commit (a PR merge ref in PR CI), not proof of a production deployment. Back/Forward reloads skip initial deep-link scrolling so the browser can restore its saved position without BFCache. Production redirect, CSP and Google URL Inspection results still require verification against the deployed final commit; a successful build does not make that claim.

## Sitemap scope

The sitemap publishes home and every independently rendered content path once, with its authored revision and visible media. Legacy aliases, media timestamp query variants and machine graph subjects are not extra HTML sitemap entries. Media URLs, video text limits, durations and publication dates are checked during generation; final validation confirms each media resource exists. A successful source build does not guarantee a particular search ranking.
